# 玉子美化 AI 协作规则

本文件约束拥有本目录读写与终端权限的 AI Agent。开始前必须读取 `prompts/0-总览与启动.md`、`data/workflow-index.json` 和当前阶段的 `requiredReads`。

## 1. 独立边界

- 只使用 `玉子美化/` 自己的依赖、Schema、检查、表格、预览、打包、回读和 CI。
- 不导入、调用或修改玉子手机 Runtime、父项目工具或父项目 `node_modules`。
- 最终合同固定为 `yuzi-beautify-preset` format v2、Runtime API v1。
- Bundle 不创建、修改或迁移数据库表，也不提供跨表读取、数据库 CRUD、AI、世界书、手机内部事件或 `AutoCardUpdaterAPI`。
- 表格 JSON、Bundle、可编辑源码始终是三份独立产物。

## 2. 引导与表达

- AI 是流程引导者，AI 不替用户作决定。表结构、制作目标、视觉方向、跳过、模拟、覆盖和最终发布等关键决定必须由用户作出；AI 可以推荐，但不得把推荐当成默认授权。
- 每完成一个用户可见阶段、每到一个决策门槛，都要主动用大白话告诉用户：现在完成了什么、建议下一步做什么、为什么这样建议、不同做法会有什么影响。不要只丢一句“接下来要做什么”。
- 默认用户没有编程基础。先说用户能看到的结果和实际影响，再补充必要技术细节；必须使用 Markdown、generated JSON、Schema、item、Runtime 等术语时，要在第一次出现时顺手解释它是什么。
- 建议要具体、可执行，并明确标注为建议。可以说明其他可行方向及代价，但最后留下一个清楚、简单的决定点给用户。
- 已经从文件、状态或用户原话中得到的信息不要重复询问。AI 负责运行命令、检查文件和解释结果，不把本项目工具能完成的技术操作转交给用户。

## 3. 三阶段强制流程

### 阶段一：接收表格、自动拆分、盘点

1. 用户已经给出有效、完整的 chatSheets 时，表格输入本身就是执行授权。AI 必须自动派生项目 ID 和显示名，先执行 `project:new --dry-run`、`project:import-tables --dry-run`，目标无冲突后立即创建草稿并正式导入；不得停在只读盘点，也不得先要求用户用自然语言说明如何拆表。只有尚未提供表格时才创建空白草稿并停在导入前。
2. 导入必须立即产生三份独立文件：未修改的 `tables/original/imported.json`、可手改的逐表 `tables/source/*.md`、从 Markdown 初始重建的 `tables/generated/tables.json`。
3. 核对原始副本、Markdown、generated JSON 深度等价，并用 `project:status --json` 展示全部表队列和 Markdown 路径。
4. 拆分完成后再询问下一步：直接开始美化并确认当前制作目标、先选择要讨论的表/美化方向，或先由用户/AI 修改 Markdown 表格文档。不得要求用户把适合直接改 Markdown 的结构调整重新口述一遍。
5. 用户选择先改表时，只编辑 `tables/source/*.md`；修改完成后由 AI 执行 build、`project:status --refresh`、草稿检查并交付重新合成的 generated 表格产物。仍存在于 generated 的表全部进入制作队列；用户明确删除的 Markdown 表在 refresh 后直接退出队列，不再额外执行 skip。

### 阶段二：严格逐表循环

- 一次只处理当前表；当前表未完成或未由用户明确跳过时，不得进入下一表。
- 每张非跳过表的用户可见流程固定为：讨论确认 → 一次制作完成 → 询问是否打开制作期模拟 → 用户确认当前表结果。字段合同和设计都在讨论确认中完成；源码实现、`project:add-item`、路径核对和一次草稿静态检查属于“一次制作完成”的内部连续动作，不逐项停顿或播报。只有失败、需要覆盖或需要用户决定时才说明。
- 需求与设计必须先充分讨论。AI 每轮集中询问一组相关问题，每个问题同时给出明确的建议答案和理由；文件、表格和项目状态中能够查明的事实由 AI 自行读取，不得反问用户。已经确认的内容不重复询问，也不得把无关问题堆成一组。
- 每张表使用 `notes/interview-<sheetKey>.md` 单独记录访谈对话。文件只按发生顺序保存访谈中“用户说了什么、AI 说了什么”的原话，不添加需求摘要、已确认决定、待确认建议、未决问题、授权状态或其他整理栏目；流程优化、命令输出和实现日志不得混入。每次访谈消息后立即追加对应原话，恢复任务或上下文压缩后必须先读完整对话，再继续访谈或实现。
- 设计总结后，AI 必须明确询问用户是否还有补充；只有用户明确表示没有补充并同意开始制作，才可编辑页面源码。用户提供想法、草图或回答单个问题本身不等于开工授权。
- 每张页面设计前必须读取 `docs/phone-ui-variables.md`，把其中的小手机尺寸、标题栏、图标和视觉变量作为全局统一参照。该文档不授予跨项目导入小手机源码的权限；所需样式和资源仍须放在当前玉子美化项目内。
- 页面源码默认只创建一个 `mount.js`，把 HTML、CSS、SVG 和交互集中在其中；确有拆分必要或用户明确要求时才增加其他页面文件。
- 每张表的需求访谈必须把 Runtime v1 提供的四个导航动作全部用大白话列给用户选择：返回上一层、上一张表、下一张表、编辑当前表。AI 可以逐项推荐，但不得因认为某项“不需要”而省略；选择过程作为双方原话自然保留在访谈对话中。
- 不得批量生成多个未经逐表确认的 item，不得批量越过需求、设计或模拟选择。
- 跳过必须由用户明确决定，记录非空原因；AI 不得根据相似度、工作量或字段缺失代替用户跳过。
- 每表都必须询问 preview。用户可以跳过；`passed/failed/skipped/not-run` 要如实记录，不能把跳过写成通过。
- 用户决定运行 preview 后，页面成功出现只是检查起点。AI 必须在预览的内存 Mock 表中自动新增至少一行有代表性的完整内容，确认页面实时更新和主要交互能够读取该行；随后自动执行一次清理/卸载与重新挂载，并检查生命周期日志、重复事件和控制台错误。以上动作连续完成，不再逐项询问用户；全部无误后才能报告 `passed`，发现问题则留在当前表修复并重新预览。

表结构修改是独立门禁：用户在拆分后明确选择先修改 Markdown，即确认进入表格准备分支；AI 自行提出的字段删除、改名或类型变化仍须先说明字段合同、现有 item、generated JSON 与数据兼容影响并取得明确确认。只编辑 `tables/source/*.md`，重建 `tables/generated/tables.json`，再执行 `project:status --refresh`。字段变化的保留表会失效并重新逐表制作；被用户明确删除的表直接从 generated 和制作队列移除。`skip-table` 只表示“表保留在 generated，但本次不制作美化”，不得用于代替删表。`tables/original/imported.json` 永远不改。

### 阶段三：汇总确认与发布

1. 队列中每张表必须是 `completed` 或 `skipped`。
2. 向用户展示完成、跳过和未模拟项，也要列出 preview failed/skipped。
3. 用户明确确认当前汇总后，才执行 `project:status --confirm`。
4. 按固定顺序执行 release check → pack → readback；任何一步失败都不得交付为正式完成。
5. 分别交付 generated chatSheets、Bundle、源码项目，并报告真实宿主仍未验证的项目。

确认摘要会随队列、字段、表结构或预览记录变化而过期；过期后必须重新汇总和确认。

## 4. 文件与覆盖纪律

- 原始输入只复制到 `tables/original/imported.json`，禁止修改。
- 表结构只改 Markdown 事实源；generated 由 `tables:cli build` 重建。
- 页面只改项目内 source/project；Bundle 由 pack 重建，不直接手改。
- 路径必须留在项目目录内，不用绝对路径、`..`、URI、反斜杠或符号链接逃逸。
- `--dry-run` 只用于建项、导入、删除或迁移、覆盖和发布等可能改变既有产物的风险动作；常规 item 登记和状态记录不重复 dry-run。目标已存在时默认拒绝覆盖，只有用户明确同意才使用对应覆盖参数。
- 保留用户工作树内已有修改；不 reset、checkout 或格式化无关文件。

## 5. 制作与模拟纪律

- 字段按 Unicode NFKC 与当前 generated 表头匹配；一张非跳过表唯一绑定一个 item。
- `project:add-item` 初次可记录 `preview-status not-run`；模拟或明确跳过后，用同一 item 的 `--replace` 更新准确状态。
- preview 只监听 `127.0.0.1`，只证明制作期模拟行为。没有真实宿主证据时，不得写“Runtime 已验证”“P8/P9 完成”或“数据库已验证”。
- preview 中自动新增的测试行只保存在当前预览进程的内存 Mock 表里，不写入 Markdown、generated JSON、原始表格、Bundle 或真实数据库。
- 真实 SillyTavern 的 CSP、路由、数据库、IndexedDB、主题叠加、滚动恢复、Blob 资源和生命周期继续标记“未验证”。

## 6. 检查与报告

- 普通用户表格修改只运行当前项目的快速链路：source check → build dry-run → build → `project:status --refresh` → 草稿检查。不要为删表、改字段等日常操作运行全仓 `npm run verify`。
- 普通页面制作只执行一次 `project:add-item` 登记和一次当前项目草稿检查，不运行全仓 `npm run verify`，也不把两步拆开向用户汇报。
- 修改 workflow、README、AGENTS 或 prompt 后运行 `npm run workflow:check`；修改工具代码时先跑相关定向测试，交付工具改动前再运行一次 `npm run verify`。
- 发布用户项目时必须使用其真实 `project.json` 执行 release check、pack、readback，不能用仓库示例绿灯代替。
- 最终报告分别列出三份交付路径、实际通过的命令、覆盖行为、制作期模拟状态、未模拟项和真实宿主待验收项。
